# BranchForge — Complete MVP Implementation Specification

## 1. Project Overview

Build **BranchForge**, an open-source, model-agnostic tree-search agentic harness that improves LLM problem-solving reliability through explicit exploration, objective feedback, backtracking, and inference-time compute allocation.

Conventional LLM agents generally follow a single reasoning trajectory. When an early assumption or implementation is wrong, they may continue refining an unproductive approach instead of exploring alternatives.

BranchForge addresses this by maintaining an explicit search tree of candidate solutions and using search algorithms to decide which branches deserve additional compute.

The initial application domain is **competitive programming**, where LLM agents generate Python solutions, execute them against test cases in isolated sandboxes, and use test feedback to improve subsequent candidates.

### Core Capabilities

The MVP must support:

1. Multiple candidate solutions to the same problem.
2. Explicit search-tree state with parent-child relationships.
3. Parallel LLM subagents exploring independent branches during beam search.
4. Isolated reasoning contexts for each subagent.
5. Feedback-guided solution refinement.
6. Objective evaluation through code execution.
7. Backtracking and pruning of unsuccessful branches.
8. Sequential Monte Carlo Tree Search (MCTS).
9. Configurable inference budgets and bounded concurrency.
10. Persistent search traces and terminal visualization.
11. Reproducible comparisons against simpler agent baselines.

### Primary Research Question

> Does explicit tree search with objective feedback improve LLM coding reliability compared with single-trajectory reasoning and independent candidate sampling, under comparable inference budgets?

### Secondary Research Question

> Can parallel branch exploration reduce wall-clock latency without changing the underlying beam-search selection policy or sacrificing correctness?

These are experimental questions, not assumptions. The system must support measuring both positive and negative results.

          +-------------+-------------+
          |             |             |

### Architectural Principles

1. The orchestrator is the sole writer of the authoritative search tree.
2. Subagents operate on independent branch contexts.
3. Search policies control exploration.
4. Workers perform candidate generation and evaluation.
5. Evaluators produce objective rewards.
6. Budgets and concurrency limits are centrally enforced.
7. Search results and decisions are persistently observable.
8. Generic search infrastructure remains independent of competitive programming.

## 5. Core Domain Models

Use strongly typed Pydantic models.

### 5.1 Problem

Define a `CodingProblem` containing:

```python
class CodingProblem(BaseModel):
    problem_id: str
    title: str
    statement: str

    input_format: str
    output_format: str
    constraints: str | None = None

    visible_tests: list[TestCase]
    hidden_tests: list[TestCase]

    time_limit_seconds: float = 2.0
    memory_limit_mb: int = 256
```

At least one visible test must be required.

The benchmark runner owns hidden tests. They must never be provided to search workers or candidate-generation prompts.

Use separate interfaces or redacted views to prevent accidental leakage of hidden tests.

### 5.2 Candidate

```python
class Candidate(BaseModel):
    candidate_id: str
    parent_candidate_id: str | None

    strategy: str | None
    explanation: str
    code: str
```

Candidates must have stable unique identifiers.

A refinement produces a new candidate rather than overwriting its parent.

### 5.3 Search Node

```python
class SearchNode(BaseModel):
    node_id: str
    parent_id: str | None

    depth: int
    children_ids: list[str]

    candidate: Candidate | None
    evaluation: EvaluationResult | None

    visits: int = 0
    total_reward: float = 0.0

    status: NodeStatus

    created_at: datetime
    updated_at: datetime
```

The root represents the unsolved problem and has no candidate or evaluation.

Separate direct evaluation rewards from accumulated MCTS statistics.

Define valid lifecycle states and transitions.

Suggested statuses:

- PENDING
- EXPANDING
- EVALUATING
- EVALUATED
- FAILED
- PRUNED

Do not conflate evaluation failure with infrastructure failure.

### 5.4 Search Tree

Implement a `SearchTree` supporting:

- Root initialization.
- Node creation.
- Parent-child relationships.
- Node lookup.
- Leaf discovery.
- Ancestor traversal.
- Path reconstruction.
- Depth validation.
- Subtree inspection.
- Serialization.
- Search statistics.

Maintain a single authoritative node registry.

Avoid duplicating entire ancestor histories inside search nodes.

Enforce tree integrity and prevent cycles.

### 5.5 Evaluation Result

```python
class EvaluationResult(BaseModel):
    candidate_id: str

    passed_tests: int
    total_tests: int

    reward: float
    test_results: list[TestResult]

    execution_time_ms: float
    error: str | None
```

A `TestResult` should contain:

- Test identifier.
- Status.
- Expected output.
- Actual output.
- Standard error.
- Exit code.
- Execution duration.
- Structured error details where relevant.

Supported statuses:

- PASS
- WRONG_ANSWER
- RUNTIME_ERROR
- TIME_LIMIT_EXCEEDED
- MEMORY_LIMIT_EXCEEDED
- INFRASTRUCTURE_ERROR

Evaluation results must be immutable once committed to the search tree.

## 6. Search Orchestrator

Implement a central `SearchOrchestrator`.

Responsibilities:

1. Initialize a search run.
2. Load and validate configuration.
3. Create the root search node.
4. Initialize the selected search policy.
5. Schedule candidate-generation or exploration tasks.
6. Coordinate evaluations.
7. Update the authoritative search tree.
8. Enforce search constraints and budgets.
9. Handle failures and cancellation.
10. Choose the final candidate.
11. Persist completed and partial run artifacts.

The orchestrator must not contain hardcoded beam-search or MCTS selection logic.

Search policies should be interchangeable.

### Search Policy Interface

Use a simple interface that permits algorithm-specific state.

For example:

```python
class SearchPolicy(Protocol):
    async def search(
        self,
        context: SearchContext,
    ) -> SearchResult:
        ...
```

The policy may coordinate selection and expansion through orchestrator-managed services.

Do not force all algorithms into an unnatural identical execution loop.

## 7. Subagent Architecture

### 7.1 Definition

A subagent is a temporary logical execution worker assigned to explore a specific branch of the search tree.

It is not itself a search node.

Each subagent may:

1. Generate a candidate.
2. Evaluate it.
3. Receive test feedback.
4. Refine the candidate.
5. Evaluate the refinement.
6. Repeat within its assigned limits.
7. Return the resulting local candidate chain.

Each meaningful candidate or refinement must become a separate global search node after the orchestrator processes the result.

### 7.2 Branch Agent Interface

Implement:

```python
class BranchAgent(Protocol):
    async def explore(
        self,
        task: BranchTask,
        budget: AgentBudget,
        cancellation: CancellationToken,
    ) -> BranchResult:
        ...
```

Define typed task, budget, result, and cancellation objects.

### 7.3 Branch Task

```python
class BranchTask(BaseModel):
    task_id: str
    problem_id: str
    parent_node_id: str

    problem_statement: str
    branch_history: list[BranchHistoryEntry]

    strategy_hint: str | None

    max_refinement_steps: int
    max_candidates: int
```

The task is an immutable snapshot of the assigned branch.

Provide the worker with the visible-test specification but never hidden benchmark tests.

### 7.4 Branch Result

```python
class BranchResult(BaseModel):
    task_id: str
    parent_node_id: str

    candidates: list[CandidateResult]

    status: BranchTaskStatus

    llm_calls: int
    input_tokens: int
    output_tokens: int

    elapsed_seconds: float
    error: str | None
```

A `CandidateResult` must contain:

- Candidate.
- Evaluation result, if available.
- Local parent candidate ID.
- Refinement step index.
- Generation metadata.

Workers must return enough information to reconstruct their local candidate chains in the global tree.

### 7.5 Context Isolation

Each subagent must have an independent `BranchContext`.

```python
class BranchContext(BaseModel):
    problem_statement: str
    strategy_hint: str | None

    history: list[BranchHistoryEntry]
    current_candidate_id: str | None
```

A worker may see:

- Original problem statement.
- Its ancestor candidates.
- Evaluation feedback along its branch.
- Assigned strategy hint.
- Its own local refinements.

It must not see:

- Private histories of unrelated workers.
- Full global search-tree state.
- Hidden tests.
- Other branches' intermediate reasoning unless explicitly supported in a future cross-branch sharing policy.

Use independent message arrays and immutable branch snapshots.

Never implement context isolation merely by changing a system prompt inside a shared mutable conversation.

### 7.6 Worker Reuse

Workers should be reusable, but branch-specific state must be reset between assignments.

A physical worker instance must not retain information from its previous branch unless explicitly included in the new task.

Use dependency injection to make this testable.

### Required Implementations

1. At least one working real-LLM provider.
2. A deterministic fake LLM for testing.

The fake provider must support predefined candidate sequences and failure scenarios.

### Structured Generation

Request candidate implementations in a structured format:

```json
{
  "strategy": "Dynamic programming",
  "explanation": "Maintain the best subarray sum ending at each position.",
  "code": "import sys\n..."
}
```

Use Pydantic validation.

Handle malformed responses with bounded retries.

Do not silently treat malformed provider responses as failed coding solutions.

### Prompt Construction

Implement two generation modes.

**Independent generation**

Create a new candidate based on the original problem.

Use optional strategy hints to encourage diversity.

**Feedback-guided refinement**

Generate a revised candidate using:

- Problem statement.
- Parent candidate.
- Parent evaluation.
- Relevant ancestor history.
- Specific failing-test feedback.

Keep prompts bounded in size.

Do not include the entire global search tree.

### Candidate Deduplication

Hash normalized code to detect exact duplicates.

Skip redundant code execution where valid evaluation results are already cached for the same task and test set.

Preserve lineage events and duplicate-attempt metadata even when evaluations are reused.

Do not assume syntactically different code is semantically identical.

## 10. Competitive Programming Environment

Implement a `CodingEnvironment` for stdin/stdout Python solutions.

### Problem Format

Support YAML problem definitions.

Example:

```yaml
problem_id: max_subarray
title: Maximum Subarray Sum

statement: >
  Given an array of integers, find the maximum sum
  of a nonempty contiguous subarray.

input_format: |
  n
  a1 a2 ... an

output_format: |
  One integer representing the maximum sum.

constraints: |
  1 <= n <= 100000
  -100000 <= ai <= 100000

visible_tests:
  - input: "5\n-2 1 -3 4 -1\n"
    expected_output: "4\n"

hidden_tests:
  - input: "3\n-5 -2 -8\n"
    expected_output: "-2\n"
```

Store held-out tests in benchmark-controlled files or objects that are not passed into the search runtime.

Support clear input/output comparison rules.

### Execution

For each candidate:

1. Validate the source code.
2. Create an isolated execution workspace.
3. Execute the code in Docker.
4. Supply test input through stdin.
5. Capture stdout and stderr.
6. Enforce execution constraints.
7. Compare output.
8. Return structured results.
9. Clean up execution resources.

### Sandbox Security

Generated Python code is untrusted.

Never execute LLM-generated code directly in the main application process.

Use Docker with:

- Networking disabled.
- Non-root execution.
- CPU limits.
- Memory limits.
- Process limits.
- Read-only root filesystem where feasible.
- Restricted writable temporary storage.
- Per-test execution timeout.
- No sensitive host mounts.
- No access to the Docker socket.
- No inherited API credentials.

Use a minimal execution image.

Do not rely on Python restricted builtins, virtual environments, or ordinary subprocesses as a security boundary.

Fail closed when Docker is unavailable.

Docker isolation is a practical MVP security measure, not an absolute defense against malicious code. Document residual risks and recommend running untrusted evaluation on a dedicated machine or stronger sandbox in higher-risk deployments.

### Test Comparison

Use exact output comparison after:

- Normalizing line endings.
- Removing trailing whitespace.

Document the exact normalization semantics.

Do not normalize arbitrary internal whitespace unless explicitly configured.

### Reward Function

Initially:

```python
reward = passed_tests / total_tests
```

Require at least one valid visible test.

Keep rewards within `[0.0, 1.0]`.

Allow future reward-function plugins.

Distinguish:

- Algorithmic failure.
- Valid partial success.
- Infrastructure failure.
- Unevaluated candidate.

An infrastructure failure should not silently receive reward zero.

### Success Semantics

Passing all visible tests means the candidate has passed the search-visible evaluation.

It does not establish full correctness.

Held-out tests are run only after final candidate selection during benchmarking.

## 11. Search Algorithms

Implement five execution modes.

### 11.1 Single-Trajectory Baseline

The baseline uses one evolving reasoning path.

Algorithm:

1. Generate one candidate.
2. Evaluate it.
3. If all visible tests pass, stop.
4. Otherwise, request a refinement using test feedback.
5. Repeat until success or budget exhaustion.

Each refinement becomes a distinct node in a linear tree.

Do not generate multiple independent branches.

Use the shared provider, evaluator, budget manager, and event logger.

### 11.2 Best-of-N Sampling

Generate up to N independent candidates from the original problem.

Candidates must not receive feedback from one another.

Evaluate candidates independently.

Select the highest-scoring evaluated candidate, using deterministic tie-breaking.

Support concurrent generation and evaluation, subject to configured limits.

This is a required baseline because it helps distinguish intelligent search from simply generating additional solutions.

### 11.3 Sequential Beam Search

Implement conventional synchronized beam search without concurrent subagents.

Configuration:

```yaml
beam_search:
  beam_width: 4
  branching_factor: 3
  max_depth: 6
  max_frontier_iterations: 4
  parallel_subagents: false
```

At each frontier:

1. Expand the surviving nodes.
2. Generate candidate continuations.
3. Evaluate candidates.
4. Rank candidates.
5. Retain the best `beam_width` candidates.
6. Prune the rest.
7. Continue to the next frontier.

Keep all pruned nodes in the tree.

Use deterministic tie-breaking.

### 11.4 Parallel-Subagent Beam Search

This is the primary feature of BranchForge.

Use a centralized orchestrator and multiple isolated branch workers.

#### Frontier-Based Execution

Implement synchronized frontier expansion:

1. Select the current beam.
2. Create expansion tasks for surviving nodes.
3. Submit tasks to the worker pool.
4. Run eligible subagent tasks concurrently.
5. Allow each subagent to generate, evaluate, and optionally refine candidates.
6. Wait for the entire frontier's assigned tasks to settle.
7. Collect all completed results.
8. Commit results to the global search tree in stable assignment order.
9. Rank eligible candidates.
10. Select the next beam.
11. Repeat until termination.

**Do not schedule additional frontier expansions merely because one worker finishes earlier than another.**

This is a synchronized parallel beam-search algorithm, not asynchronous best-first search.

#### Local Refinements

Each subagent may perform multiple bounded refinements.

For example:

```text
Parent Node
   |
   +-- Candidate A1
          |
          +-- Candidate A2
                 |
                 +-- Candidate A3
```

All candidates must appear as separate global search nodes.

Define depth as the number of candidate transitions from the root.

A local refinement must count toward search depth.

The `max_depth` constraint applies to intermediate candidates, not merely frontier transitions.

#### Branching Semantics

Use explicit, consistent rules:

- `branching_factor`: Maximum number of immediate children generated from a node in one expansion.
- `max_candidates_per_task`: Maximum total candidates produced in one branch assignment, including refinements.
- `max_refinement_steps`: Maximum refinement transitions along a local chain.
- `beam_width`: Maximum number of surviving nodes in each new frontier.

The worker must not exceed these constraints.

A worker assigned to one parent may generate multiple first-level alternatives, and optionally refine them, subject to its total candidate budget.

Represent the resulting local structure explicitly rather than assuming all returned candidates form one linear chain.

#### Frontier Selection

Default policy:

- Consider eligible evaluated candidates produced during the completed frontier.
- Rank by visible-test reward.
- Use stable deterministic tie-breaking.
- Exclude candidates whose evaluations are invalid.
- Enforce beam width.
- Mark unselected candidates as pruned.

Do not carry older frontier nodes forward by default.

An optional future elitism policy may be supported, but keep it disabled in the MVP.

#### Parallel Configuration

```yaml
beam_search:
  beam_width: 4
  branching_factor: 3
  max_depth: 6
  max_frontier_iterations: 4

  parallel_subagents: true

  subagent:
    max_concurrent: 4
    max_refinement_steps: 2
    max_candidates_per_task: 3

  elitism: false
```

#### Strategy Diversity

The orchestrator may assign strategy hints such as:

- Dynamic programming.
- Greedy.
- Graph traversal.
- Two pointers.
- Binary search.
- Divide and conquer.
- Brute force with optimization.

Hints should be contextually relevant.

Do not force a candidate to follow an inappropriate algorithm simply for diversity.

Avoid extra LLM calls for strategy selection in the initial implementation.

#### Successful Candidate Handling

For reproducible behavior, finish the current frontier before stopping on visible-test success.

Do not immediately cancel other frontier workers solely because one candidate passes all visible tests.

At the synchronization barrier, select the best candidate and terminate if the success criterion is met.

An aggressive cancellation mode is outside the MVP scope.

### 11.5 Sequential Monte Carlo Tree Search

Implement MCTS using Upper Confidence Bounds applied to Trees (UCT).

Selection formula:

\[
UCT(i)=\frac{W_i}{N_i}
+c\sqrt{\frac{\ln N_p}{N_i}}
\]

Where:

- \(W_i\) is cumulative rollout reward.
- \(N_i\) is visit count.
- \(N_p\) is parent visit count.
- \(c\) is the exploration constant.

Handle unvisited children explicitly.

#### MCTS Iteration

**Selection**

Traverse the tree using UCT until an expandable node is found.

**Expansion**

Generate a new candidate child.

Respect branching-factor and maximum-depth limits.

**Evaluation**

Execute the candidate against visible tests.

Use direct evaluation reward as the MVP's shallow rollout reward.

**Backpropagation**

Update cumulative reward and visit counts along the selected path.

Each completed simulation must backpropagate exactly once.

#### Configuration

```yaml
mcts:
  exploration_constant: 1.414
  max_simulations: 30
  branching_factor: 3
  max_depth: 5
```

Clearly distinguish:

- Direct evaluation reward.
- Simulation reward.
- Total accumulated reward.
- Mean node value.

#### MCTS Concurrency

Run one MCTS simulation at a time.

Do not implement:

- Virtual loss.
- Parallel tree selection.
- Shared-tree parallel rollouts.
- Concurrent MCTS backpropagation.

MCTS may reuse the LLM provider, evaluator, tree models, and budget manager.

Do not require MCTS to use the parallel subagent pool.

## 12. Search Tree Consistency

The central orchestrator must be the sole writer of global search-tree state.

Subagents return structured results but do not mutate shared nodes.

When committing branch results:

1. Verify the task ID.
2. Verify the originating parent node.
3. Validate candidate IDs.
4. Validate local parent references.
5. Validate local topology.
6. Enforce depth and branching limits.
7. Detect duplicate candidate code.
8. Create corresponding global nodes.
9. Attach evaluation records.
10. Record events.

### Deterministic Commit Ordering

Worker completion order is nondeterministic.

After a beam frontier completes, commit results in stable task-assignment order.

Within a task, preserve deterministic local candidate order.

Assign stable logical ordering metadata.

Persist both actual event timestamps and logical commit sequence numbers.

Given the same ordered branch results and configuration, tree structure and beam selection should be deterministic.

Real LLM outputs themselves are not guaranteed to be reproducible.

### Preserving Failed Branches

Do not delete failed or pruned branches.

The saved tree must make it possible to answer:

- What candidates were generated?
- Which candidates failed?
- Why did they fail?
- What refinements were attempted?
- Which branches were pruned?
- Why was the final candidate selected?

## 13. Budget Management

Implement a shared `SearchBudget` manager.

### Global Limits

```yaml
budget:
  max_llm_calls: 60
  max_tokens: 150000
  max_cost_usd: 3.00
  max_wall_time_seconds: 300
  max_candidates: 60
```

### Per-Subagent Limits

```yaml
agents:
  max_concurrent: 4

  per_task_budget:
    max_llm_calls: 5
    max_candidates: 3
    max_wall_time_seconds: 90
```

### Required Accounting

Track:

- LLM calls.
- Input tokens.
- Output tokens.
- Total tokens.
- API cost when known.
- Candidate count.
- Evaluation count.
- Wall-clock time.
- Per-worker consumption.

### Concurrency-Safe Reservations

Multiple workers may request resources simultaneously.

Use atomic reservations or an asyncio lock around shared budget state.

Before dispatching a model request:

1. Check applicable global and local limits.
2. Reserve capacity.
3. Execute the request.
4. Reconcile actual resource consumption.
5. Record the result.

Do not allow race conditions to exceed hard LLM call or candidate-count limits.

Token and cost accounting require additional care because actual consumption may not be known until a request completes.

For strict token admission control, reserve conservative upper bounds.

If exact pricing is unavailable, report unknown cost rather than zero.

Do not claim guaranteed hard dollar enforcement when costs cannot be bounded accurately before calls.

### Fairness

For synchronized beam search, allocate equal per-task maximum budgets to surviving branches by default.

Do not give faster workers extra opportunities.

If the remaining global budget cannot support all assignments, apply a deterministic admission policy and record skipped tasks.

### Termination Reasons

Define:

- SUCCESS
- MAX_LLM_CALLS
- MAX_TOKENS
- MAX_COST
- MAX_WALL_TIME
- MAX_CANDIDATES
- SEARCH_EXHAUSTED
- USER_CANCELED
- ERROR

Persist the final termination reason.

Stop scheduling new work when applicable limits are exhausted.

Handle in-flight operations according to the documented reservation and cancellation policy.

## 16. Benchmarking

The benchmark system must compare:

1. Single-trajectory baseline.
2. Best-of-N.
3. Sequential beam search.
4. Parallel-subagent beam search.
5. Sequential MCTS.

### Metrics

Measure:

- Visible-test success rate.
- Mean LLM calls per problem.
- Mean input and output tokens.
- Mean API cost where available.
- Mean wall-clock latency.
- Mean candidate evaluations.
- Average search depth.
- Maximum concurrent workers.
- Termination-reason distribution.

### Visible vs. Held-Out Tests

This distinction is mandatory.

**Visible tests** guide candidate generation, refinement, and search rewards.

**Held-out tests** are only executed after a final candidate has been selected.

The search engine must not have access to hidden test input, expected output, or hidden evaluation feedback.

Prefer physically separating benchmark-only test data from the search runtime's problem representation.

### Example Problems

Include at least five problems:

1. Maximum subarray sum.
2. Balanced parentheses.
3. Two Sum.
4. Shortest path in an unweighted graph.
5. Minimum coin change.

Each problem must have:

- Clear statement.
- Input/output specification.
- Constraints.
- Multiple visible tests.
- Multiple hidden tests.
- Relevant edge cases.
- A validated reference solution.

### Experimental Fairness

Compare algorithms using:

- The same LLM model.
- The same task set.
- The same visible and hidden test splits.
- Comparable inference budgets.
- Consistent evaluation rules.

For a robust comparison, include both:

**Cost-matched experiments:** Similar token or API spending limits.

**Latency-oriented experiments:** Compare wall-clock time and success under concurrent execution.

Parallelism by itself is not expected to increase accuracy.

Use repeated trials where practical.

Record model versions, configuration, seeds, timestamps, and environment versions.

Do not fabricate benchmark improvements or imply that preliminary results establish general effectiveness.

- Unvisited-child selection.

- Candidate limits.

- Reservation cleanup.

## 19. Engineering Quality Standards

### Correctness

- Do not silently swallow exceptions.
- Do not invent successful evaluation results.
- Do not double-count token usage.
- Do not double-apply MCTS backpropagation.
- Do not exceed hard candidate or LLM-call limits through races.
- Do not create inconsistent parent-child relationships.
- Do not let canceled workers mutate completed global state.
- Do not leak hidden benchmark tests.

### Async Execution

- Use bounded concurrency.
- Avoid blocking the event loop.
- Manage all spawned tasks.
- Ensure cleanup during errors and cancellation.
- Avoid unbounded queues.
- Keep concurrency primitives simple and explicit.

### Architecture

- Separate search algorithms from providers.
- Separate search state from worker-local state.
- Separate evaluation from generation.
- Keep environments replaceable.
- Keep search policies testable using fake providers.
- Favor composition over inheritance.
- Avoid speculative extensibility.

### Security

- Treat generated code as untrusted.
- Use Docker isolation.
- Do not expose host credentials.
- Disable network access for candidate execution.
- Enforce resource limits.
- Clean up execution environments.
- Fail closed if sandboxing cannot be established.

### Documentation

Document:

- Project motivation.
- Architecture.
- How parallel subagents work.
- Difference between workers and search nodes.
- Beam search and MCTS behavior.
- Installation requirements.
- Docker setup.
- Provider configuration.
- CLI usage.
- Testing.
- Benchmark methodology.
- Security limitations.
- Known constraints.
- Roadmap.

Provide an example that works without API credentials.
